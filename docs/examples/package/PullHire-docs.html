Реализация отвечает на требование о «понятном разделении на Frontend, Backend (API-сервисы бизнес-логики) и слой хранения» (docs/requirements/nonfunctional.md, «Архитектура»).

1. Обзор системы

1.1. Состав сервисов

Платформа построена как микросервисная система: восемь бизнес-сервисов, API-шлюз и SPA для обеих ролей.

  • auth-service - идентичность, JWT, роли, согласия 152-ФЗ.
  • candidate-service - профиль и резюме, настройки приватности.
  • fsp-service - шов интеграции с реестром ФСП и достижения.
  • assessment-service - тестирование, грейд, cooldown, категория; регулярные задания [ext].
  • selection-service - каталог, категории, ранжирование, подборка.
  • employer-service - компания и потребность в найме.
  • outreach-service - приглашения и выход на контакт; вакансии и классический отклик [ext].
  • notification-service - исходящая электронная почта.
  • api-gateway (Nginx) - единая входная точка.
  • frontend (SPA) - веб-приложение для кандидата и работодателя.

Каждый бизнес-сервис - отдельное приложение на Java 21 + Spring Boot, собираемое Gradle, с Spring AMQP (RabbitMQ), Flyway (миграции в своей схеме), springdoc-openapi (документирование), JJWT (RS256) и хешированием паролей Argon2id/BCrypt. Детали и версии - в docs/stack.md.

1.2. Текстовая схема (диаграмма)

Browser SPA -> api-gateway (Nginx) -> {auth, candidate, fsp, assessment,
      selection, employer, outreach, notification}
  sync REST/JSON (JWT RS256, проверка локально по кэшу JWKS)
  async: RabbitMQ topic exchange
    user.registered · user.email_verified · consent.updated ·
    candidate.card_updated · candidate.contact_released ·
    fsp.linked · fsp.achievements_updated ·
    assessment.category_assigned · assessment.grade_changed ·
    invitation.{sent,viewed,accepted,declined}
  storage: PostgreSQL (схема и роль на сервис) + volume файлов

1.3. Ключевые потоки

  • Онбординг кандидата. assessment-service проводит опрос, выбор грейда и тест; событие assessment.category_assigned через outbox попадает в проекцию категорий selection-service, после чего карточка становится видимой работодателю. Событие fsp.achievements_updated запускает переранжирование (см. docs/testing_model.md, docs/selection.md).
  • Подбор (LHH). Работодатель вызывает POST /selections в selection-service; сервис формирует ранжированную подборку и пояснения из собственных проекций. Затем POST /invitations в outreach-service запускает приглашение (см. docs/selection.md).
  • Выход на контакт. Кандидат принимает приглашение; invitation.accepted → candidate-service выдаёт раскрытие контактов → candidate.contact_released → outreach-service сохраняет контакты для работодателя, а notification-service уведомляет кандидата.

2. Микросервисы vs монолит: обоснование

ТЗ приветствует микросервисную архитектуру, но допускает монолит (docs/requirements/nonfunctional.md, «Архитектура»). Выбор сделан в пользу микросервисов и подкреплён четырьмя неоднородными швами, а не формальной «галочкой»:

  • fsp-service - граница внешней интеграции, перепроектируемая после хакатона.
  • notification-service - иной режим отказа и изоляция SMTP-доступа.
  • assessment-service - второй по весу оцениваемый компонент (25%) с собственным движком.
  • selection-service - событийная read-модель, естественная для ранжирования.

Риски компенсированы осознанно: 8 сервисов (не 12), четыре свёрнутых модуля (§3.4), один PostgreSQL, единый стек, отсутствие mesh, распределённого трейсинга и K8s, smoke-тест compose как воспроизводимая проверка. Честная цена решения - примерно +2 недели интеграции против монолита, окупаемые лучшей технической оценкой и наглядной схемой для жюри.

Запасной путь. При отставании схлопываются employer-service → outreach-service и fsp-service → candidate-service; контракты событий при этом сохраняются.

3.2. api-gateway

Единая точка входа на Nginx:

  • терминация TLS (демо - self-signed сертификат);
  • маршрутизация запросов к сервисам;
  • статический rate-limit;
  • сквозной заголовок X-Request-Id;
  • индекс документации /docs со ссылками на OpenAPI сервисов.

Шлюз не выполняет роль BFF: сервисы самостоятельно валидируют JWT локально по кэшированному JWKS (§6.1). Дополнительный слой агрегации не вводится (см. §4.1).

3.3. frontend (SPA)

Веб-приложение на React/Next.js для обеих ролей с маршрутизацией по роли (кандидат/работодатель). Прямых обращений к сервисам минуя шлюз нет. Клиенты к API строятся по сгенерированным OpenAPI-спецификациям (§4.4). UI-конвенции наследуются от RoboMatch (внешний вид в этом документе не описывается). Реализация сценариев - в docs/user_flow.md.

3.4. Свернутые модули (folds) и пути выделения

Чтобы не порождать лишние контексты, четыре модуля свёрнуты в соседние сервисы. Для каждого документирован путь обратного выделения:

  • taxonomy → selection-service. Справочники специализаций и грейдов живут рядом с категориями. Выделение возможно, если каталог станет самостоятельным доменом; контракты assessment.category_assigned и candidate.card_updated при этом сохраняются.
  • files → candidate-service. Хранение файлов резюме реализовано сменным адаптером; при росте объёмов адаптер заменяется на внешнее хранилище без изменения остальных сервисов.
  • periodic tasks → assessment-service [ext]. Движок регулярных заданий переиспользует планировщик и форматы заданий. Выделяется в tasks-service при отдельном жизненном цикле; интерфейс жёсткий: задания не пишут в грейд/категорию (docs/periodic_tasks.md).
  • vacancies/apply → outreach-service [ext]. Вакансии и классический отклик - модуль внутри LHH-контура. Выделяются в vacancy-service, если сценарий выйдет из статуса «плюс» в основной; при этом сохраняется единая механика контактов.

4. Взаимодействие сервисов

4.1. Синхронное взаимодействие (REST)

  • Только REST/JSON. gRPC отклонён как избыточный для MVP (YAGNI).
  • Поток запроса: браузер → api-gateway → сервис.
  • Внутренние синхронные вызовы сведены к минимуму на горячих путях за счёт read-моделей-проекций. Единственная цепочка «по требованию»: потребность работодателя → POST /selections (сервис читает собственные проекции).
  • Оговорка: «единственная цепочка по требованию» действует для ядрового контура. Опциональная механика регулярных заданий [opt] добавляет внутренний sync-GET employer → assessment для сигнала свежести (docs/periodic_tasks.md §6.4).
  • Обнаружение сервисов не вводится: DNS Docker Compose и статические маршруты Nginx; K8s/Consul отклонены для MVP.

4.2. События: RabbitMQ, конверт, идемпотентность

  • Брокер - RabbitMQ, topic exchange, доставка at-least-once.
  • Конверт события: {event_id, type, version, occurred_at, producer, correlation_id, payload}.
  • Идемпотентность потребителей обеспечивается по event_id.
  • JSON-схемы событий лежат в contracts/events/ и проверяются в CI.

Хореография единственного многосервисного сценария (принятие приглашения): invitation.accepted → candidate-service выдаёт раскрытие контактов → candidate.contact_released → outreach-service сохраняет контакты → notification-service уведомляет кандидата. Управляющий оркестратор не вводится; поведение описано в docs/selection.md и docs/data_model.md §9.

4.3. Transactional outbox и итоговая согласованность

Для событий, потеря которых критична, применяется transactional outbox:

  • assessment.category_assigned;
  • жизненный цикл приглашения (invitation.sent/viewed/accepted/declined).

Согласованность проекций selection-service - итоговая: кандидат невидим работодателю до assessment.category_assigned, а фронтенд гейтит отображение по статусу. Это принятое следствие выбора read-модели, а не дефект.

4.4. Контракты: OpenAPI и JSON Schema событий

  • OpenAPI каждого сервиса генерируется springdoc-openapi автоматически; на шлюзе собирается индекс /docs.
  • Из спецификаций строятся TypeScript-клиенты для SPA.
  • Событийные контракты - JSON Schema в contracts/events/; совместимость проверяется в CI (§7.3), изменения фиксируются в docs/backlog/closed_questions.md.

5. Топология контейнеризации (TOPOLOGY A)

5.1. Состав контейнеров docker-compose

core:
  frontend (nginx) · gateway (nginx) ·
  auth · candidate · fsp · assessment ·
  selection · employer · outreach · notification   (Spring Boot JARs) ·
  postgres  (1 контейнер: схемы auth|candidate|fsp|assessment|

  • Целевой объём памяти ≈ 2.0–2.2 ГБ RAM.
  • Одноразовый контейнер seed наполняет каталог идемпотентно.
  • Команды сборки и запуска - в docs/deployment.md; версии образов - в docs/stack.md.

5.2. PostgreSQL: схема и роль на сервис

Один контейнер PostgreSQL, логическая изоляция:

  • у каждого сервиса своя схема: auth, candidate, fsp, assessment, selection, employer, outreach, notification;
  • у каждой схемы отдельная роль БД; сервис подключается только своей ролью;
  • жёсткая конвенция: нет кросс-схемных JOIN и внешних ключей между схемами; доступ к чужим данным - только через API или события.

Данные и связи внутри схем - в docs/data_model.md.

5.3. Healthcheck, зависимости и лимиты памяти

  • На каждом сервисе: /healthz (liveness) и /readyz (готовность БД и брокера).
  • В compose используется depends_on: service_healthy.
  • Для контейнеров задан mem_limit.
  • Целевой суммарный footprint - около 2 ГБ (§5.1), что согласуется с требованием «удерживать память в разумных пределах» (docs/requirements/nonfunctional.md, «Аппаратные требования»).

5.4. Миграция TOPOLOGY A → B

TOPOLOGY B - физический PostgreSQL на сервис. Переход выполняется без переписывания кода:

  • жёсткая конвенция отсутствия кросс-схемного доступа (§5.2) делает разделение конфигурационным;
  • шаги: перенос PGDATA соответствующей схемы в отдельный инстанс и обновление строк подключения в конфигурации сервиса;
  • сервисные и событийные контракты не меняются.

Решение о TOPOLOGY A обосновано бюджетом памяти, единой резервной копией и логической изоляцией на старте (реестр решений - docs/assumptions.md).

6. Безопасность и 152-ФЗ

6.1. Аутентификация: JWT RS256, JWKS, пароли

  • Регистрация по email с подтверждением адреса; модерация работодателей на этапе MVP не требуется (docs/requirements/acceptance.md).
  • Токены: JWT RS256 с коротким TTL и refresh-токеном; публичный ключ публикуется как /.well-known/jwks.json.
  • Форма claim совместима с Keycloak (sub, realm_access.roles, JWKS) - упрощает будущую интеграцию с ФСП ID (docs/requirements/nonfunctional.md, «Аутентификация»).
  • Пароли хранятся как Argon2id/BCrypt.
  • Проверка ролей (candidate/employer) выполняется по claim-ам JWT.
  • Схема интеграции с ФСП - в docs/fsp_integration.md.

6.2. Согласия и приватность

  • Согласие на обработку данных фиксируется при регистрации (auth-service), изменения согласий аудируются.
  • Область видимости («что видно») принадлежит candidate-service; событие candidate.card_updated несёт только согласованные поля, так что поисковый индекс selection-service структурно не может утечь PII.
  • Раскрытие контактов происходит только через событие candidate.contact_released - то есть после принятия приглашения или самостоятельного отклика кандидата [ext] (правила ролей в docs/data_model.md §12).
  • Хранение и обработка - на инфраструктуре на территории РФ (локализация по 152-ФЗ).

6.3. Сетевые границы: gateway, TLS, роли БД

  • Внешний трафик входит только через api-gateway; TLS терминируется на нём (демо - self-signed).
  • Сервисы валидируют JWT локально по кэшу JWKS, не ходя на auth-service на каждый запрос.
  • Разграничение доступа к данным обеспечено ролями БД на схему (§5.2); кросс-схемный доступ запрещён конвенцией.

7. Наблюдаемость, конфигурация и CI

7.1. Логи, X-Request-Id, health/metrics

  • Структурированные JSON-логи.

7.2. Конфигурация и секреты (12-factor)

7.3. CI (GitHub Actions)

Конвейер на каждый сервис:

  • линтер/форматтер → сборка и тесты (Java: build + test);

  • сборка Docker-образа;

Smoke-тест одновременно закрывает требование «по запросу жюри команда демонстрирует запуск и работу кода» (docs/requirements/nonfunctional.md, «Качество кода»). Состав smoke и e2e детализирован в docs/deployment.md; e2e-сценарий покрывает путь docs/testing_model.md §1.

8. Производительность и платформенность

Ориентиры MVP (docs/requirements/nonfunctional.md, «Производительность», «Платформенность»):

Конвейер обязателен при регистрации: категория кандидата определяется не самоописанным резюме, а прохождением всех этапов (docs/requirements/overview.md, Постановка задачи; docs/requirements/testing.md).

  • Тест проводится на заявленный грейд; кандидат не может быть понижен принудительно (§7.2).

Вакансии служат лишь демонстрационным контекстом, а не источником генерации заданий.

2. Входные этапы

2.1. Опрос

  • Опрос по отрасли и специализации заполняется до теста (docs/requirements/testing.md).
  • Результат опроса задаёт specialization кандидата и набор заявленных измерений, которые обязана покрывать форма попытки (§4).
  • Ответы опроса — вход для подбора пула семейств шаблонов (§3.4) и границ категорий (§6.2).
  • Хранение опроса: test_sessions.survey_answers и test_sessions.declared_dimensions (docs/data_model.md §6.1); отрасль кандидата — candidate.profiles.industry_code (docs/data_model.md §4.1).

2.2. Самообъявленный грейд

  • Кандидат самостоятельно выбирает предполагаемый грейд (docs/requirements/overview.md, Постановка задачи).
  • declared_grade задаёт целевую сложность: стартовая точка θ маршрутизации (§5.1) и набор полос для отображения (§6.2).
  • Самообъявление не является результатом: итоговый грейд определяется оценкой θ по cut-score, а не выбором кандидата.

3. Банк заданий

3.1. Форматы заданий

Содержание и формат заданий команда определяет сама; допустимы задачи с кодом, опросники и иные форматы (docs/requirements/testing.md, «Формат заданий»). В продукте закрытые форматы проверяются автоматически, а открытые (свободный ответ, подход) — вручную либо полуавтоматически:

Формат Проверка Примечание
Одиночный/множественный выбор Автоматическая Ключ задаётся шаблоном, не LLM (§3.6)
Короткий ответ (число/строка) Автоматическая Ключ нормализуется вручную
Задача с кодом Автоматическая (тесты) + проверка схожести Схожесть — §9.1
Свободный ответ / подход Вне MVP-формы грейд-теста В MVP живёт в периодических заданиях работодателей (docs/periodic_tasks.md); extension [ext] — §3.6, §9.2
  • Форма MVP-грейд-теста состоит только из автопроверяемых форматов (закрытые вопросы, короткий ответ, задачи с кодом). Свободный ответ («предложить подход») в MVP-форму грейд-теста не входит и остаётся в продукте только внутри периодических заданий работодателей, где оценивает работодатель (docs/periodic_tasks.md).
  • Пул заданий грейд-теста строго отделён от пула регулярных заданий (docs/periodic_tasks.md) — общими являются только инфраструктурные примитивы.
  • Ключ оценивания (правильный ответ) никогда не попадает в клиент.

3.2. Структура задания: шаблон-«радикал» и параметры-«инцидентали»

Задание описывается кортежем (concept, template, parameters, difficulty):

  • Шаблон («радикал»), template family — неизменяемая структура задания: формулировка, правило решения, логика ключа.
  • Параметры («инцидентали»), incidentals — переменные значения внутри шаблона (числа, имена, данные примеров). Меняют поверхность, не сложность.
  • Варианты одного шаблона — изоморфы: различаются поверхностью, сохраняют предназначенную сложность b.
  • Для каждой попытки сохраняется уникальный seed, с которым сгенерированы параметры (docs/data_model.md §6.1). По seed задание воспроизводимо.

Такое разделение снимает конфликт «утечка ↔ сопоставимость»: поверхностная уникальность достигается генерацией, структурная сложность остаётся общей.

3.3. Якорные задания

  • Якорные задания, anchor items — небольшая защищённая подборка, включённая в каждую форму попытки.
  • Сложность якорей подтверждена экспертами и фиксирована; они не генерируются из шаблонов.
  • Якоря служат основой эквайтинга между попытками (§9.3) и обнаружения дрейфа при пересчёте (§3.5).
  • В адаптивном режиме раскрытие ответов и параметров якорей недопустимо — используется защищённый показ без adaptive-выдачи (§9.1).

3.4. Семейства шаблонов и уникальные seed вариантов

  • Банк двухслойный: (а) защищённые якорные задания (§3.3); (б) крупные семейства шаблонов, дающие неограниченный поток вариантов.
  • Каждое семейство порождает изоморфы с общим b; параметры варианта определяются per-item seed.
  • Различаются два уровня seed: seed формы test_sessions.form_seed (form-level, воспроизводимость сборки формы) и seed варианта attempts.variant_seed (per item, параметры конкретного задания). Повторная выдача того же параметрического варианта одному кандидату не допускается: assessment-service ведёт журнал выдач в разрезе «кандидат × семейство шаблонов/seed» и не переиздаёт уже выданный вариант (docs/data_model.md §6.1).
  • Число доступных вариантов на семейство шаблонов и лимиты выдачи регулируются exposure caps на уровне семейства/задания (item_bank.exposure_limit / item_bank.exposure_count), а не отдельного несуществующего варианта (§9.1).

3.5. Начальная калибровка и пересчет (provisional loop)

  • Начальная сложность заданий задаётся экспертной оценкой и помечается provisional.
  • Пересчёт (refit) сложностей выполняется по логам ответов с опорой на якорные задания (§3.3); якоря связывают шкалы попыток и позволяют обнаруживать дрейф сложности.
  • До накопления достаточного объёма данных не заявляется точность IRT: сложности остаются провизорными.

3.6. Политика применения LLM

  • LLM допускается только для заполнения поверхностных инциденталей внутри уже зафиксированной модели задания (шаблона).
  • LLM никогда не определяет ключ оценивания (правильный ответ) и не назначает сложность b.
  • Полностью сгенерированные LLM задания, оценка которых также делегирована LLM, запрещены (см. §9.5).
  • Оценка свободных ответов LLM допускается только как [ext]-расширение (вне MVP): облачный LLM-API (российский), с пиннингом версии модели и логом хеша промпта на каждый вердикт, temperature = 0, ответ структурированным JSON строго по фиксированной человеческой рубрике. LLM и в этом режиме никогда не определяет ключ оценивания и не назначает сложность b.
  • Локальный хостинг LLM исключён из MVP требованиями к железу (docs/requirements/nonfunctional.md).

4. Сборка формы попытки

Форма попытки собирается под конкретного кандидата и его declared_grade. Правила сборки:

  • Покрытие заявленных измерений: форма обязана покрывать измерения, заявленные в опросе (§2.1), без перекоса в одно.
  • Не более одного варианта на семейство в форме — предотвращает дублирование логики решения.
  • Перемешивание: порядок заданий и порядок вариантов ответа перемешиваются для каждой попытки.
  • Exposure caps: лимит показов задаётся на уровне семейства шаблонов / задания (item_bank.exposure_limit / item_bank.exposure_count); при исчерпании задание (семейство) выводится из ротации (§9.1).
  • Якоря: в форму всегда включается защищённый якорный набор (§3.3).
  • Seed: для каждой формы сохраняется form-level test_sessions.form_seed (воспроизводимость сборки и разбирательство); параметры отдельных заданий — per-item attempts.variant_seed (§3.4).
  • Собранная форма фиксируется в сущности попытки (docs/data_model.md §6.1).

5. Адаптивная маршрутизация (IRT-lite, 1PL)

Маршрутизация — упрощённая однонаправленная модель IRT (1PL, Rasch). Это осознанное упрощение для MVP: параметры различения не оцениваются.

5.1. Оценка θ и выбор следующего задания

  • Вероятность правильного ответа:

    p(correct) = 1 / (1 + exp(-(θ − b)))

  • θ — уровень кандидата; b — сложность задания; старт — со среднего уровня относительно declared_grade.

  • После каждого задания θ обновляется упрощённым байесовским шагом (для MVP); переход на MLE/LBFGS — в расширениях.

  • Следующее задание выбирается с сложностью, ближайшей к текущей оценке: минимум |θ − b| среди доступных вариантов.

5.2. Правила остановки

  • Остановка происходит при достижении порога стандартной ошибки SE.
  • Одновременно действуют минимум и максимум числа заданий: форма не завершается раньше минимума и принудительно завершается на максимуме.
  • Значения порога SE и границ числа заданий — документированные константы (docs/assumptions.md).

5.3. Fallback: многоэтапное тестирование (MST)

Если адаптивная маршрутизация недоступна или упрощается для MVP, применяется многоэтапное тестирование, multistage testing:

  • 2–3 фиксированные панели разной сложности;
  • переключение между панелями по результату предыдущего этапа (routing);
  • сохраняются якоря (§3.3) и правила остановки по объёму (§5.2).

6. Оценивание: скоринг → грейд

6.1. Отчет θ + SE (не проценты)

  • Результат теста выражается оценкой θ и её стандартной ошибкой SE.
  • Процент правильных ответов не является итоговой метрикой и не отображается как результат.
  • θ, SE и связанные данные попытки сохраняются (docs/data_model.md §6.1) для аудита и пересчёта.

6.2. Cut-score и категории-полосы

  • Шкала θ разбивается на полосы грейдов документированными cut-score.
  • Полоса отображается в кандидатскую категорию: категория = специализация × грейд; семантика категории — в docs/selection.md.
  • Cut-score документируются для прозрачности и справедливости (docs/assumptions.md).

6.3. «Требует перепроверки» (SE завышен / CI на границе полосы)

  • Если SE завышен или доверительный интервал θ пересекает границу полосы — попытка помечается как «требует перепроверки», а не принудительно относится к грейду.
  • В спорных случаях решение принимает человек в контуре (ручная проверка); автоматика не выносит пограничный вердикт.

7. Повышение и понижение грейда

7.1. Правила up/down

  • Кандидат, не прошедший тест на заявленный уровень, может пройти тест на уровень ниже; кандидат, справившийся уверенно, — повысить грейд (docs/requirements/testing.md, «Повышение и понижение грейда»).
  • Повышение и понижение выполняются по инициативе кандидата через новую попытку тестирования; автоматического пересмотра нет.
  • Категория (= специализация × грейд) пересчитывается по результату любой завершённой попытки, включая up/down и повторные попытки.
  • Контракт событий: любая завершённая попытка перепубликует assessment.category_assigned с актуальной категорией; для проекции категории selection потребляет это событие (полный список консьюмеров — docs/architecture.md §3.1). assessment.grade_changed — audit/notification only и на обновление категории не влияет.
  • Изменения грейда фиксируются в истории (docs/data_model.md §6.1), публикуется событие assessment.grade_changed (аудит/уведомление).
  • В MVP повышение/понижение грейда опирается только на автопроверяемые форматы (закрытые вопросы, короткий ответ, код); свободный ответ в грейд-тест не входит (§3.1).

7.2. Запрет принудительного понижения

  • По результату теста грейд не понижается принудительно (docs/requirements/overview.md, Постановка задачи).
  • Провал теста на заявленный грейд не отображает кандидата в более низкий грейд автоматически: система лишь предлагает пройти тест на уровень ниже.
  • Кандидат, не прошедший тест на заявленном грейде, не имеет категории, пока не пройдёт тест хотя бы на каком-либо грейде; UI при этом подсказывает более низкий уровень.

7.3. Cooldown = 1 месяц

  • Смена грейда ограничена по времени: cooldown = 1 месяц (утверждённое решение команды; требование допускает выбор интервала — docs/requirements/testing.md, «Ограничение смены грейда»).
  • Cooldown контролируется через таблицу cooldowns в схеме assessment (docs/data_model.md §6.1), а не через поля истории грейда.
  • Повторная попытка смены грейда до истечения cooldown недоступна; правило отражено в API проверки права (/assessment/grade-eligibility).

8. Присвоение категории

  • По результату теста определяется полоса грейда и присваивается категория кандидата — связка специализации и грейда (§6.2); при needs_review — ручное решение (§6.3).
  • Категория (= специализация × грейд) обновляется по итогу любой завершённой попытки, включая повышение/понижение грейда и повторные попытки.
  • В MVP категория выводится только из автопроверяемых форматов (§3.1); свободный ответ в грейд-тест не входит и на присвоение категории не влияет.
  • Завершением конвейера считается публикация события assessment.category_assigned (transactional outbox; docs/architecture.md §4.3); каждая завершённая попытка перепубликует это событие с актуальной категорией; для проекции категории selection потребляет его (полный список консьюмеров — docs/architecture.md §3.1).
  • assessment.grade_changed — audit/notification only: на проекцию категории в selection не влияет (§7.1).
  • Событие транслируется в selection-service как проекция категории; до его публикации кандидат невидим в поиске.
  • Документ завершается на этом событии: определение категории, внутрикатегорийное ранжирование, подборка и выход на контакт — вне рамок и описаны в docs/selection.md.
  • Категория — единственный сигнал грейд-тестирования, видимый работодателю; результаты попытки и θ работодателю не раскрываются.

9. Целостность и сопоставимость

9.1. Защита от утечек

  • Уникальные per-item seed вариантов (attempts.variant_seed, §3.4) — поверхность задания не повторяется.
  • Exposure caps — лимит показов на уровне семейства шаблонов / задания (item_bank.exposure_limit / item_bank.exposure_count), вывод из ротации при исчерпании.
  • Перемешивание порядка заданий и вариантов ответа (§4).
  • Проверка схожести свободных ответов и кода: принимается готовый инструмент (JPlag/Dolos), собственный детектор не разрабатывается.
  • Ключи оценивания не попадают в клиент; в адаптивном режиме ответы не раскрываются.
  • Принимаемый остаточный риск: кратковременная утечка конкретного задания (семейства шаблонов) ограничена ротацией и exposure caps.

9.2. Прокторинг-флаги и человеческая проверка

  • Фиксируются прокторинг-флаги с отметками времени:
    • visibilitychange — уход со страницы;
    • выход из полноэкранного режима (fullscreen exit);
    • вставка из буфера (paste).
  • Флаги формируют сигнал для человеческой проверки, а не вердикт.
  • Автоматический провал по одному флагу запрещён («never auto-fail»); решение принимает человек в контуре.
  • Очередь человеческой проверки свободных ответов [ext]: пакетная проверка в рабочие часы со SLA 24–48 рабочих часов (не 24/7).
  • Автоматический вердикт по свободному ответу [ext] допустим только на порогах ≥ 8/10 или ≤ 3/10; всё, что между, а также любой прокторинг-флаг → человек в контуре.
  • Fallback при недоступности API: задание исключается из скоринга, попытка пересчитывается (безопасно за счёт якорей и эквайтинга, §9.3).

9.3. Эквайтинг по якорным заданиям

  • Якорные задания (§3.3) включены в каждую форму и связывают попытки между собой.
  • По ответам на якоря выполняется эквайтинг — приведение оценок разных попыток к общей шкале.
  • Якоря также служат опорой при пересчёте сложностей и обнаружении дрейфа (§3.5).

9.4. Сопоставимость кандидатов: θ как общая шкала

  • Сопоставимость обеспечивается отчётом θ (и SE), а не процентом правильных ответов (§6.1).
  • Общая шкала θ позволяет сравнивать кандидатов, проходивших разные формы, в том числе с разными наборами параметрических вариантов.
  • Полосы cut-score (§6.2) переводят общую шкалу в категории.

9.5. Антипаттерны

  • Единый фиксированный набор заданий для всех кандидатов.
  • Полностью LLM-сгенерированные задания, оцениваемые LLM.
  • Отчёт в процентах как итоговый результат.
  • Заявление точности IRT на малых выборках.
  • Отсутствие контроля показов (exposure control).
  • Автоматический провал по одному прокторинг-флагу.
  • Расчёт только на перемешивание как единственную защиту.
  • Таймированный полный CAT без минимума/максимума заданий.
  • Игнорирование политики применения LLM (§3.6).
  • Свободный ответ в MVP-грейд-тесте без гарантированного механизма проверки.
  • Переиспользование seed параметров и раскрытие ответов в адаптивном режиме.
  • Публичные глобальные лидерборды.
  • Автоматизация кадровых решений без человека в контуре.

Регулярные задания работодателей

Назначение документа

Документ описывает механику регулярных коротких заданий от работодателей: каденс и синхронные окна, жизненный цикл задания работодателя, добровольную подписку кандидата, случайный розыгрыш задания, формы ответа и оценку, атрибут свежести профиля, сигнал работодателю и защиту от «игры с механикой».

Связанные документы: docs/testing_model.md (граница механики грейд-тестирования), docs/data_model.md (сущности и поля), docs/selection.md (категории и ранжирование), docs/mvp_scope.md (границы MVP), docs/user_flow.md (сквозные сценарии), docs/assumptions.md (реестр решений), docs/glossary.md (термины).

Источники: docs/requirements/testing.md («Регулярные задания»), docs/requirements/roles.md (роли «Кандидат», «Работодатель»), docs/requirements/overview.md (постановка задачи).

Вне рамок: механика грейд-тестирования и присвоения категории (docs/testing_model.md), формула ранжирования внутри категории (docs/selection.md), физическая схема сущностей и DDL (docs/data_model.md).

1. Обзор механики и задействованные сущности

Помимо первичного тестирования, определяющего грейд и профиль, система периодически предлагает кандидату короткую задачу от работодателя: решить её или предложить подход к решению. Механика поддерживает профиль кандидата в актуальном состоянии и даёт работодателю свежий сигнал о кандидате — «желательно, но не обязательно для MVP» (docs/requirements/roles.md).

Жёсткое правило (hard rule). Результаты регулярных заданий НИКОГДА не изменяют грейд, категорию и историю грейда (grade_history). Единственное, что обновляется по итогам задания, — атрибут свежести профиля ProfileFreshness. См. §6.3.

Сущности механики — TaskCycleConfig, EmployerTaskPrompt, Task, TaskVersion, TaskAssignment, TaskSubmission, TaskInterestSubscription, ProfileFreshness — определены (поля, ключи, ограничения, UNIQUE) в docs/data_model.md §6.2–6.3. Здесь их состав не дублируется; сущности используются только по ссылке. ProfileFreshness размещается в схеме assessment (см. docs/data_model.md §6.3).

Жёсткая граница с docs/testing_model.md. docs/testing_model.md владеет первичным конвейером (опрос → заявленный грейд → тест), анти-утечкой и сопоставимостью, скорингом → грейдом, запретом принудительного понижения и cooldown, присвоением категории. Настоящий документ владеет жизненным циклом заданий работодателя, подпиской, розыгрышем, ответами, свежестью и сигналом работодателю. Интерфейс: чтение факта «у кандидата есть категория»; записи в грейд/категорию/cooldown — отсутствуют. Общие примитивы — только инфраструктурные (планировщик, таксономия форматов заданий, UI ответа) и заимствованные принципы анти-утечки. Пулы задач строго отделены от банка заданий грейд-теста.

2. Каденс и синхронные окна (A)

Параметр Значение Примечание
n 7 дней глобальная константа платформы
Дедлайн d n срок ответа на выданное задание
Окна глобальные синхронные не per-account rolling
TZ единая платформенная timestamps в UTC, границы окон — в TZ платформы
  • A1. Глобальная константа n = 7 дней управляет обоими каденсами: промптами работодателя по вакансиям и выдачами заданий кандидатам.
  • A2. Окна глобальные синхронные (не индивидуальные rolling-окна) — это обеспечивает идемпотентность через cycle_date.
  • A3. Ежедневный планировщик открывает и продвигает циклы; все записи — идемпотентные upsert-ы, повторный запуск или сбой планировщика не создаёт дублей.
  • A4. Единая таймзона платформы: timestamps хранятся в UTC, границы циклов отсчитываются в TZ платформы; таймзона документируется (см. docs/assumptions.md).

3. Цикл задания работодателя (B)

3.1. Промпт {add | update | keep}

  • B1. В момент открытия окна для каждой активной вакансии создаётся промпт с выбором действия {add | update | keep}; уникальность UQ(vacancy_id, cycle_date) гарантирует ровно один промпт на вакансию в окне (см. docs/data_model.md §6.2).
  • B3. Неразрешённый промпт истекает при закрытии окна, при этом задание остаётся активным. Отложенное расширение: пометка «устаревшее» после m проигнорированных промптов ([ext], см. §9).

3.2. Версии задания (TaskVersion)

  • B2. Действия над заданием:
    • add → создаётся задание Task версии v1;
    • update → создаётся новая неизменяемая (immutable) TaskVersion с version_no++, предыдущие версии сохраняются;
    • keep → явное подтверждение без новой версии, инкремент keep_count.
  • Версия, выданная кандидату, неизменяема: правки не задним числом, а новой версией.

3.3. Отставление задания (retire)

  • B4. Работодатель может отставить (retire) задание; то же происходит автоматически при закрытии вакансии. Отставленное задание исключается из новых выдач, но уже открытые назначения доводятся до дедлайна против выданной версии (см. §8).

3.4. Запрет адресной выдачи

  • B5. Работодатель НЕ может адресно выдать задание конкретному кандидату — только системный случайный розыгрыш (§5). Это предотвращает обход LHH-механики выхода на контакт и гейтинга контактов (docs/selection.md, docs/requirements/roles.md, правило 2).

4. Подписка кандидата (C)

  • C1. Участие — opt-in, переключатель по умолчанию ВЫКЛЮЧЕН (DEFAULT OFF). Тип согласия — task_participation (docs/data_model.md §3.4), покрывает участие и отображение результата; отписка прекращает будущие выдачи.
  • C2. Участие возможно только при наличии завершённой первичной категории (пройдены опрос и тест). Без категории кандидат в розыгрыш не попадает.
  • C3. Пул задач ограничивается специализацией кандидата. [ext] Фильтр по грейду — опционально.

5. Розыгрыш задания (D)

5.1. Одна выдача на окно

  • D1. Раз за окно каждый подписанный и правомочный кандидат получает ровно одно задание, выбранное равномерно случайно (uniform-random) из множества: активное ∧ (активная вакансия ∨ активная «потребность» работодателя через Task.need_id — fallback-якорь, docs/assumptions.md §11) ∧ обязательное совпадение специализации ∧ ещё не проходил ∧ не заблокировано «устаревшим» заданием. Уникальность UQ(candidate_id, cycle_date).

5.2. Дедупликация на уровне задания

  • D2. «Непройденное» определяется на уровне ЗАДАНИЯ (task-level): если кандидат пытался решить задание в любой из его версий, оно больше никогда не предлагается.

5.3. Дедлайн d = n и возврат в пул

  • D3. Дедлайн ответа d = n. При отсутствии ответа задание помечается expired и возвращается в доступный пул. [ext] Лимит повторных предложений (re-offer cap) = 2.

5.4. Пустой / исчерпанный пул; лимит повторов [ext]

  • D4. Если пул пуст или исчерпан, выдача не создаётся, кандидат видит «задач нет», повторная попытка — в следующем окне. [ext] Ограничение повторов (§5.3) сужает пул дополнительно.

6. Выполнение и свежесть профиля (E)

6.1. Формы ответа: «решить» / «предложить подход»

  • E1. Две формы ответа: «решить» или «предложить подход к решению». Обе считаются успешной сдачей (passed). [ext] Минимальный порог усилия (min-effort floor).

6.2. Оценка работодателем

  • E2. Оценка выполняется работодателем вручную (автоматически — где формат это позволяет). Результат: positive / negative / unreviewed.

6.3. Свежесть профиля: display-only

Жёсткое правило (hard rule). Результаты заданий НИКОГДА не изменяют грейд, категорию и историю грейда (grade_history); обновляется только атрибут свежести ProfileFreshness.

  • E3. Записи в грейд/категорию/grade_history по итогам задания запрещены (повтор §1).
  • E4. При сдаче обновляется ProfileFreshness.last_task_activity_at = now; отображается бейдж «актуальный профиль: {дата} / N задач».
  • E5. Свежесть по умолчанию — display-only: НЕ входит в ранжирование категории. [ext] Опциональный ограниченный recency-decay требует отдельного согласования (sign-off).

6.4. Сигнал работодателю

  • E6. Представление сигнала показывает работодателю недавнюю активность по заданиям. Данные лежат в схеме assessment; у employer-service проекции нет, событие не определено. Путь чтения задаётся одним из двух вариантов: (а) [opt] внутренний sync-GET из employer-service в assessment-service — вызов не на горячем пути, поэтому согласуется с минимизацией внутренних синхронных вызовов (docs/architecture.md §4.1); либо (б) проекция представления в схеме работодателя, наполняемая событием [ext]. Контактные данные кандидата остаются закрытыми — гейтинг контактов не меняется (docs/requirements/roles.md, правило 2; docs/selection.md).

7. Защита от «игры с механикой» (F)

  • F1. Одна выдача на кандидата в окно (UQ(candidate_id, cycle_date)).
  • F2. Задания привязаны к вакансиям; адресная выдача кандидату запрещена.
  • F3. Свежесть по умолчанию не даёт рангового выигрыша (§6.3).
  • F4. Утечка содержания заданий принята как остаточный риск: задания короткие и обновляются каждые n дней; требование анти-утечки относится к грейд-тесту, а не к этой механике.
  • F5. Минимальный порог усилия применяется, если свежесть становится видимой.

9. MVP и отложенные расширения

Вся механика — optional-MVP (критерий 6, 7%), но проектируется полностью уже сейчас (см. docs/mvp_scope.md).

  • Минимальный срез: B1–B4, C1–C2, D1–D4, E1–E4, F1/F2.
  • Отложено: автоматическое истечение «устаревших» заданий, [ext] фильтры scope, ранговый recency-decay, лимиты повторов (re-offer cap), автоматизация min-effort, email-уведомления, персональные таймзоны.

Флаг зависимости. ТЗ привязывает задания к вакансиям, но публикация вакансий сама по себе optional-MVP. Fallback [ext]: якорить задание к «описанию потребности» (needs) или к компании, а не к опубликованной вакансии. Решение фиксируется в docs/assumptions.md §11.

1. Обзор механики

Платформа связывает напрямую только работодателя и соискателя. Онбординг кандидата (опрос → заявленный грейд → тест) завершается публикацией события assessment.category_assigned; с этого момента кандидат становится видимым. Работодатель описывает потребность, получает подборку с объяснимостью и сам выходит на контакт, направляя приглашение конкретному человеку — инициатива принадлежит работодателю (LHH), а не кандидату.

Ключевые инварианты механики:

  • Кандидат невидим работодателям до события assessment.category_assigned. До присвоения категории он не попадает ни в поиск, ни в подборку (docs/testing_model.md §8).
  • Выдача строится на категориях, а не на самоописанном резюме. Поиск и подборка опираются на присвоенную категорию, подтверждённую тестом, а не на ключевые слова резюме (docs/requirements/selection.md, «Поиск и фильтрация банка кандидатов»).
  • Контактные данные кандидата закрыты до принятия приглашения или самостоятельного отклика кандидата (docs/requirements/roles.md, правило 2).
  • Свежесть профиля не влияет на позицию в ранжировании (§3).

Текстовая схема потока:

Работодатель:  описание потребности
               -> POST /selections (selection-service читает свои проекции)
               -> подборка: рекомендованные категории + кандидаты + объяснимость
               -> поиск и фильтры по банку
               -> приглашение: описание, зарплата (обязательно), способ связи
Кандидат:      принятие приглашения
               -> invitation.accepted -> candidate.contact_released
               -> контакты раскрыты работодателю

Владельцы контекстов: selection-service — каталог (taxonomy), проекции категорий и карточек, ранжирование и формирование подборки; outreach-service — приглашения, их статусы и раскрытие контактов. Согласованность проекций — итоговая, через события (docs/architecture.md §4.3).

2. Категории кандидатов

Категория — это группа однотипных соискателей, в основе которой связка специализации и грейда (например, «бэкенд-разработчики с опытом», «фронтенд-разработчики с опытом до года»). Формально category = specialization × grade.

  • Категория не выводится из самоописанного резюме. Она определяется обязательным путём при регистрации: опрос по отрасли и специализации, самостоятельный выбор предполагаемого грейда и тест на заявленный грейд; результат автоматически определяет категорию, видимую работодателю (docs/requirements/selection.md, «Категории кандидатов»).
  • Справочник специализаций и грейдов команда составляет самостоятельно, опираясь на общепринятые в ИТ понятия; на этапе MVP достаточно основных направлений. Справочник хранится в selection.taxonomy (docs/data_model.md §7.1); его состав — решение команды (docs/assumptions.md).
  • Проекция текущей категории кандидата — selection.candidate_categories (docs/data_model.md §7.2); она наполняется событием assessment.category_assigned и является источником для поиска и подборки.
  • Карточка кандидата в поисковой проекции (selection.candidate_cards, docs/data_model.md §7.3) не содержит PII: контактные данные в неё не попадают (docs/data_model.md §12).

Контракт события. Для проекции категории selection-service потребляет assessment.category_assigned; полный список консьюмеров — docs/architecture.md §3.1. Событие перепубликуется по любой завершённой попытке — включая повышение грейда, понижение грейда и повторные попытки, — с актуальной категорией. Событие assessment.grade_changed является audit/notification only и на обновление категории в selection не влияет (docs/testing_model.md §7.1, §8).

Кандидат без присвоенной категории (в том числе не прошедший тест на заявленный грейд) в поиске и подборке отсутствует. Понижение грейда не выполняется принудительно: система лишь предлагает пройти тест на уровень ниже, а категория появляется после любой успешно завершённой попытки (docs/testing_model.md §7.2).

3. Ранжирование внутри категории

Ранжирование выполняется внутри категории: сравниваются кандидаты одной специализации и одного грейда. Кандидаты разных категорий между собой по позиции не сопоставляются.

Входы ранжирования — сила подтверждённого профиля:

  • Подтверждённый результат теста — оценка θ (и SE) как общая шкала (docs/testing_model.md §6.1, §9.4). Выше находится кандидат с более сильным подтверждённым уровнем.
  • Подтверждённые достижения ФСП — наличие и количество проверяемых достижений участника соревнований и мероприятий ФСП (docs/fsp_integration.md §5).

Свойства ранжирования:

  • Свежесть профиля НЕ является входом ранжирования. Результаты регулярных заданий обновляют только атрибут ProfileFreshness, который по умолчанию display-only и участия в позиции не принимает (docs/periodic_tasks.md §6.3, docs/data_model.md §6.3).
  • Самоописанные данные резюме (самостоятельно указанный грейд, ключевые слова стека и т.п.) на позицию не влияют: ранжирование опирается на подтверждённый профиль. Стек используется для фильтрации (§5), а не для повышения позиции.
  • Отсутствие истории ФСП нейтрально и не является штрафом; достижения — это дополнительное преимущество, а не обязательное условие (docs/fsp_integration.md §6).
  • Компоненты ранжирования хранятся в selection.rank_signals (docs/data_model.md §7.4); конкретные веса и константы формулы — документированные параметры (docs/assumptions.md).
  • Обновление достижений запускает событие fsp.achievements_updated, по которому карточка переранжируется (docs/architecture.md §4.2).

4. Формирование подборки

4.1. Вход: описание потребности

Входом формирования подборки служит описание потребности работодателя: какие специалисты нужны, чем занимается команда, требуемые стек, специализация и грейд (docs/requirements/selection.md, «Формирование подборки»; docs/requirements/roles.md, «Работодатель»). Потребность хранится в employer.needs (docs/data_model.md §8.2) и принадлежит employer-service.

Синхронный путь: потребность передаётся в selection-service запросом POST /selections (docs/api.md §3.5), который читает собственные проекции и возвращает подборку. Единственная синхронная цепочка «по требованию» в архитектуре — именно она (docs/architecture.md §4.1). Никаких cross-schema JOIN не выполняется: сервис использует только свои проекции (docs/data_model.md §1).

4.2. Правила формирования

  • Отбор. В подборку попадают только категоризированные кандидаты, у которых специализация совпадает со специализацией потребности, а грейд соответствует требуемому. Кандидаты без категории не рассматриваются (§2).
  • Фильтрация по стеку. Требуемый в потребности стек уточняет набор кандидатов; совпадение стека — фильтр, а не сигнал позиции (§3).
  • Ранжирование. Кандидаты ранжируются внутри категории по силе подтверждённого профиля (§3); в выдачу попадает верхняя часть ранжированного списка (top-N).
  • Две формы выдачи. Подборка показывает и рекомендованные категории, и конкретных кандидатов (docs/requirements/selection.md, «Работа с подборкой кандидатов»).
  • Уточнение без потери. Фильтрация и уточнение запроса выполняются без потери ранее полученной подборки (docs/requirements/selection.md, «Поиск и фильтрация банка кандидатов»).
  • Состав выдачи — категория, специализация, грейд, подтверждённые достижения ФСП; результаты попытки и θ работодателю не раскрываются (docs/testing_model.md §8).

4.3. Объяснимость включения и позиции

Каждый кандидат в подборке сопровождается краткой объяснимостью: почему он попал в выдачу и почему стоит на своей позиции (docs/requirements/selection.md, «Объяснимость ранжирования и выдачи»). Объяснимость опирается на те же входы, что и ранжирование (§3), и не требует раскрытия внутренних параметров модели:

  • совпадение категории (специализация × грейд) с потребностью;
  • подтверждённый результат теста как основание позиции;
  • наличие подтверждённых достижений ФСП;
  • совпадение требуемого стека.

Объяснимость — часть критерия 1 (35 %): она делает ранжирование проверяемым и понятным работодателю (docs/requirements/evaluation.md, критерий 1).

5. Поиск и фильтры по банку кандидатов

Работодателю доступен весь банк категоризированных кандидатов с фильтрацией (docs/requirements/selection.md, «Поиск и фильтрация банка кандидатов»). Доступные фильтры:

Фильтр Основание
Специализация категория кандидата (docs/data_model.md §7.2)
Грейд категория кандидата (docs/data_model.md §7.2)
Категория связка специализация × грейд (docs/data_model.md §7.1)
Стек поисковая проекция карточки (docs/data_model.md §7.3)
Наличие подтверждённых достижений ФСП сигналы ранжирования (docs/data_model.md §7.4)
  • Выдача строится на основании категорий, присвоенных по итогам опроса и тестирования, а не на основании самоописанных данных резюме.
  • Результаты поиска ранжируются по степени соответствия описанной потребности с краткой объяснимостью (§4.3).
  • Предусмотрены фильтрация и уточнение запроса без потери ранее полученной подборки.
  • Контактные данные в банке не показываются; их раскрытие возможно только через приглашение или отклик (§6.3, docs/data_model.md §12).

6. LHH: выход работодателя на контакт

LHH-механика — смысловой центр решения: инициативу проявляет не кандидат, а работодатель. Работодатель просматривает категоризированную базу и сам направляет приглашение конкретному человеку (docs/requirements/overview.md, «Постановка задачи»). Это принципиально отличается от прямого отклика кандидата на вакансию и является главным критерием оценки (docs/requirements/evaluation.md, критерий 1).

6.1. Приглашение: обязательные поля

Приглашение направляется конкретному кандидату и содержит обязательные поля (docs/requirements/roles.md, правила 1–2):

  • описание предложения (message);
  • уровень заработной платы — диапазон «от–до», в рублях, указывается обязательно; кандидат видит условия до начала общения (принципиальное отличие сервиса);
  • название компании (company_name);
  • способ связи — снимок контактных данных работодателя на момент создания приглашения (employer_contact).

Приглашение не требует обязательной привязки к опубликованной вакансии (docs/requirements/roles.md, «Выход на контакт»). Поля хранятся в outreach.invitations (docs/data_model.md §9.1); «способ связи» — единственный снимок, поскольку cross-schema JOIN запрещён (docs/data_model.md §1). Здесь состав полей не дублируется: источник — docs/data_model.md §9.1.

6.2. Жизненный цикл приглашения

Приглашение отслеживается по статусам, отражающим ход взаимодействия; каждая сторона видит актуальный статус только по своим записям (docs/requirements/roles.md, правило 3).

Статус Смысл Событие
sent приглашение отправлено invitation.sent
viewed кандидат просмотрел invitation.viewed
accepted кандидат принял invitation.accepted
declined кандидат отклонил invitation.declined
expired приглашение истекло —

Перечисления статусов и типов событий — сводный указатель docs/data_model.md §11 (статус приглашения outreach.invitations.status, §9.1; тип события outreach.invitation_events.event_type, §9.2). Переходы статусов фиксируются в append-only журнале outreach.invitation_events (docs/data_model.md §9.2, §13). Критичные события жизненного цикла приглашения публикуются через transactional outbox, поскольку их потеря недопустима (docs/architecture.md §4.3).

6.3. Раскрытие контактов

Контактные данные кандидата раскрываются работодателю только в двух случаях (docs/requirements/roles.md, правило 2):

  1. кандидат принял приглашение (accepted); либо
  2. кандидат сам откликнулся на вакансию — классический поток, реализуемый как расширение [ext].

Хореография раскрытия при принятии приглашения (docs/architecture.md §4.2):

invitation.accepted
   -> candidate-service выдаёт раскрытие контактов
   -> candidate.contact_released
   -> outreach-service сохраняет контакты (released_contact, contact_released_at)
   -> notification-service уведомляет кандидата

До раскрытия контакты хранятся только в candidate.profiles и не передаются работодателю; поисковая проекция структурно не содержит PII (docs/data_model.md §12). Отклик кандидата, если реализован, также раскрывает контакты и фиксируется в outreach.applications (docs/data_model.md §9.3) — модуль [ext].

Валидация

1. Цели и область валидации

Валидация отвечает на четыре вопроса, сформулированных в ТЗ (docs/requirements/evaluation.md, критерий 2):

  1. Стабильность теста — даёт ли тест согласованный результат при повторном прохождении (§3).
  2. Дискриминативность — насколько задания разделяют слабых и сильных кандидатов (§4).
  3. Соответствие экспертной оценке / эталонной разметке — согласуется ли результат с независимой экспертной разметкой команды (§2, §6).
  4. Релевантность подборки — какова доля релевантных кандидатов в топе выдачи на собственном наборе пар «вакансия – кандидат» (§5).

Область: Решение D. Валидируются только автопроверяемые форматы — задачи с кодом, закрытые вопросы и короткий ответ. Именно из них состоит MVP-форма грейд-теста. Свободный ответ («предложить подход») в MVP-грейд-тест не входит и в валидацию грейд-теста не попадает; он оценивается только как [ext]-расширение по фиксированной человеческой рубрике (LLM-вердикт лишь на порогах, спорные случаи — на ручную проверку). Решение D зафиксировано в docs/assumptions.md; границы форматов — docs/mvp_scope.md §2.4, §3.1; опциональные ML/NLP-расширения вынесены за границу MVP (docs/mvp_scope.md §3.4). Валидация [ext]-оценки свободных ответов выходит за пределы текущих результатов и описывается отдельно.

Что не входит в область: автоматизация кадровых решений (человек в контуре обязателен), проверка боевой интеграции с ФСП, оценка UX и нефункциональных характеристик.

3. Процедура: стабильность теста

Проверяется согласованность результата при повторном прохождении (docs/requirements/evaluation.md, критерий 2).

  • Test–retest. Одни и те же кандидаты проходят тест на тот же заявленный грейд дважды; сравниваются грейд-полосы и оценки θ.
  • Параллельные формы. Формы собираются из одних и тех же семейств шаблонов с обязательным общим набором якорных заданий; параметрические варианты различаются, структурная сложность сохраняется (docs/testing_model.md §3.4, §4).
  • Эквайтинг. Оценки разных форм приводятся к общей шкале по якорным заданиям (docs/testing_model.md §9.3), поэтому сравнение θ между формами корректно.

Метрики:

Метрика Что измеряет
Совпадение грейд-полосы, % доля кандидатов с той же полосой при повторе
Коэффициент согласия κ (Cohen) согласие полос сверх случайного
Корреляция θ (Spearman) устойчивость рангового порядка
Среднее ` Δθ

Стабильность считается достаточной, если повтор не меняет грейд-полосу в большинстве случаев, а θ высоко коррелирует между формами. Это описательные метрики: при малой выборке они не дают оснований для заявлений о точности IRT (§7).

4. Процедура: дискриминативность

Проверяется, насколько задания и якоря разделяют слабых и сильных (docs/requirements/evaluation.md, критерий 2), а калибровка не «плывёт».

  • Разделение групп. Кандидаты сортируются по итоговой θ; сравниваются верхняя и нижняя группы (трети или крайние 27 %).
  • Индекс дискриминативности задания. D = p(верно | верхняя группа) − p(верно | нижняя группа) по каждому заданию и шаблонному семейству.
  • Точечно-бисериальная корреляция ответа на задание с θ — дополнительный сигнал разделяющей способности.
  • Дискриминативность якорей. Для защищённых якорных заданий проверяется ожидаемо высокая разделяющая способность.
  • Калибровочный дрейф. Сложности b пересчитываются (refit) по логам ответов с опорой на якоря (docs/testing_model.md §3.5); дрейф = расхождение между экспертной b и пересчитанной. Для непересчитанных заданий параметры остаются provisional.
Метрика Смысл
Индекс дискриминативности D разделение групп по заданию
Точечно-бисериальная корреляция связь задания с общей шкалой
D якорных заданий качество опорной подборки
Калибровочный дрейф ` Δb

Задания с низкой дискриминативностью и якоря с заметным дрейфом попадают в очередь ревью (замена/перекалибровка). Пороги фиксируются в docs/assumptions.md.

5. Процедура: релевантность подборки

Проверяется качество выдачи на собственном наборе пар «вакансия – кандидат» (docs/requirements/evaluation.md, критерий 1; тестовый набор доля релевантных в топе выдачи).

  • Для каждой потребности из набора система формирует подборку (docs/selection.md §4) — рекомендованные категории и конкретных кандидатов с объяснимостью.
  • Выдача сопоставляется с эталонной разметкой пар (§2): считается доля релевантных кандидатов в топе.
  • Baseline. Для сравнения используется наивное ранжирование по совпадению ключевых слов резюме/стека; преимущество показывает вклад подтверждённого профиля и LHH-ранжирования.
  • Объяснимость (качественная проверка). Для выборки подборок проверяется, что краткая объяснимость соответствует фактическим основаниям включения и позиции (docs/selection.md §4.3).

Precision@k (P@k) доля релевантных среди первых k

7. Ограничения валидации

  • Малые выборки. Числа повторных попыток и пар «вакансия – кандидат» невелики, поэтому результаты описательные. Точность IRT не заявляется: параметры заданий остаются provisional, о сходимости и инвариантности параметров утверждать нельзя (docs/testing_model.md §3.5).
  • Синтетические данные. Набора и эталонной разметки от организатора нет; данные собственные, поэтому переносимость на реальный рынок не гарантируется (docs/requirements/acceptance.md).
  • Только автопроверяемые форматы. Свободные ответы в MVP не валидируются; их [ext]-оценка (LLM по фиксированной рубрике) требует отдельной процедуры (Решение D, docs/assumptions.md; docs/mvp_scope.md §2.4).
  • Мало якорей. Эквайтинг и обнаружение дрейфа опираются на небольшую защищённую подборку; расширение якорного набора — направление развития (docs/testing_model.md §3.3).
  • Субъективность разметки. Экспертная разметка заданий и пар зависит от состава экспертов; число экспертов ограничено.
  • Один срез. Прогон единичный, без лонгитюдного наблюдения и A/B с реальными работодателями; результаты — не замена продакшен-калибровке.

1. Общая схема интеграции

Организатор намеренно не предоставляет ни API, ни описание структуры данных ФСП (docs/requirements/profiles.md; docs/requirements/acceptance.md, «Ресурсы организатора»). Поэтому «схема интеграции» в решении - это не готовый контракт, а граница сервиса fsp-service: изолированный шов, за которым спрятан сменный адаптер реестра. Такое решение выбрано осознанно (docs/architecture.md §3.1, §3.4) и перепроектируется после хакатона без затрагивания остальных сервисов.

Взаимодействие строится так:

  • синхронно: браузер → api-gateway → fsp-service (REST/JSON) для связывания ФСП ID и чтения достижений;
  • асинхронно: fsp-service публикует события fsp.linked и fsp.achievements_updated в RabbitMQ; проекция selection-service переранжирует карточку кандидата (docs/architecture.md §4.2).
Кандидат -> api-gateway -> fsp-service
   |  POST /candidate/fsp/link  (привязка ФСП ID)
   |  GET  /candidate/fsp/achievements  (чтение кэша)
   v
fsp-service -> registry adapter (mock сегодня, боевой - после хакатона)
   |  fsp.linked               -> candidate-service / audit
   |  fsp.achievements_updated -> selection-service (переранжирование)
   v
PostgreSQL схема fsp (fsp_links, achievements_cache)   [docs/data_model.md §5]

Сервис не хранит PII работодателя и не принимает решений о найме: он лишь поставляет обогащение профиля, а правила видимости остаются за candidate-service и selection-service (docs/data_model.md §12).

2. Аутентификация: совместимость с Keycloak

В дальнейшем ФСП ID будет работать на базе Keycloak, поэтому совместимость с этим решением упростит интеграцию, но это ориентир, а не требование: выбор способа авторизации остаётся за командой (docs/requirements/nonfunctional.md, «Аутентификация»; docs/requirements/profiles.md, «Связь с ID участника ФСП»).

Рекомендации по совместимости (не обязательства):

  • форма claim-ов JWT совместима с Keycloak: sub, realm_access.roles;
  • публичный ключ публикуется как /.well-known/jwks.json, сервисы проверяют подпись локально по кэшу JWKS (docs/architecture.md §6.1);
  • связь с реестром выполняется через отдельный fsp_id, независимо от выбранного способа аутентификации (docs/data_model.md §5.1).

Практический смысл: если команда выберет Keycloak-совместимую схему, переход на реальный ФСП ID сведётся к подключению внешнего identity provider без переписывания fsp-service. Если выбран другой способ авторизации, интеграция всё равно возможна - через сопоставление fsp_id.

3. Принятая модель данных ФСП

Поскольку структура данных реестра не выдана, команда приняла собственную модель - это документированное допущение (docs/assumptions.md). Хранение описано в docs/data_model.md §5 (единственный источник полей и ограничений); здесь фиксируется только смысл и обоснование.

  • fsp_links - связь кандидата с ID участника ФСП. Поля link_status (pending, linked, unlinked, error) и history_status (unknown, present, no_history) отделяют техническое состояние связи от наличия истории достижений; это прямое следствие обязательной обработки случая «нет истории» (§6).
  • achievements_cache - кэш достижений для отображения: title, event_type, achieved_at, place, payload. Поле payload типа jsonb оставляет свободу под неизвестную заранее структуру реального реестра; пустой набор достижений допустим при history_status = no_history.

Модель намеренно плоская и устойчива к неизвестному контракту: если боевой реестр вернёт другую структуру, меняется только маппинг в адаптере, а не таблицы (§7).

4. Мок-реестр и синтетические данные

Готовый API ФСП на хакатоне недоступен (docs/requirements/acceptance.md, «Элементы, прорабатываемые самостоятельно»), поэтому реестр эмулируется.

  • Mock-адаптер. fsp-service работает против адаптера, реализующего тот же интерфейс, что и будущий боевой клиент. Для MVP это детерминированный мок, отвечающий на привязку и выдачу достижений.
  • Синтетический seed. Одноразовый контейнер seed (docs/architecture.md §5.1) наполняет схему fsp идемпотентно и синтетическими данными: набор кандидатов с историей достижений (history_status = present) и отдельный набор без истории (history_status = no_history) для проверки §6.
  • События. Результат привязки и обновления достижений всегда отражается событиями fsp.linked и fsp.achievements_updated (docs/architecture.md §1.2), поэтому реальный источник данных не влияет на реакцию остальных сервисов.

Синтетические данные - собственные данные команды, что прямо разрешено условиями (docs/requirements/acceptance.md, «Элементы, прорабатываемые самостоятельно»).

5. Отображение достижений

Автоматическое обогащение профиля достижениями ФСП даёт работодателю дополнительный ориентир при оценке, а участнику соревновательного движения - возможность конвертировать спортивный опыт в карьерное преимущество (docs/requirements/profiles.md, «Достижения ФСП в профиле»).

  • Достижения показываются работодателю в карточке кандидата: название, тип события, дата, место (если применимо). Формат отображения - часть творческой задачи и может уточняться.
  • Показ подчиняется согласиям и настройкам приватности кандидата: без согласия достижения не попадают в публичную/поисковую проекцию (docs/data_model.md §12).
  • Обновление достижений запускает событие fsp.achievements_updated, по которому selection-service переранжирует карточку (docs/architecture.md §4.2).

6. Отсутствие истории: обработка

Корректная обработка случая, когда истории ФСП у кандидата нет, обязательна (docs/requirements/profiles.md, «Связь с ID участника ФСП»). Правила:

  • отсутствие истории фиксируется явно как history_status = no_history и отличается от технической ошибки link_status = error;
  • отсутствие истории нейтрально для ранжирования: достижения ФСП - это дополнительное преимущество, а их отсутствие не является штрафом и не понижает категорию кандидата;
  • отсутствие истории не блокирует ни онбординг, ни присвоение категории, ни видимость карточки работодателю;
  • в интерфейсе состояние «достижений нет» показывается отдельно от состояния «данные недоступны», чтобы работодатель не трактовал сбой как отсутствие достижений.

7. Путь к боевой интеграции

После хакатона интеграция дорабатывается совместно с ФСП (docs/requirements/acceptance.md, «Что вне MVP»). Архитектурный шов fsp-service спроектирован так, чтобы изменения были локализованы.

Что меняется при появлении реального реестра:

  • Адаптер. Заменяется mock на боевой клиент API реестра; интерфейс сервиса и его эндпоинты (docs/api.md §3.3) не меняются.
  • Аутентификация. При подтверждении Keycloak-варианта подключается внешний identity provider; при другом варианте - сопоставление fsp_id (§2).
  • Маппинг данных. Реальная структура достижений отображается в принятую модель; при необходимости корректируется наполнение payload, а базовые поля (title, event_type, achieved_at, place) остаются стабильным контрактом (docs/data_model.md §5.2).
  • Синхронизация. Разовая загрузка при привязке дополняется периодической или событийной синхронизацией; по-прежнему публикуется fsp.achievements_updated.

Что не меняется: потребители события (selection-service), candidate-service, публичные контракты и правила видимости. Это и есть ценность выделенной границы: реальная интеграция не требует переписывания остальной системы (docs/architecture.md §3.4).

1. Общие соглашения

  • Стиль. Только REST/JSON поверх HTTPS; тела — application/json в кодировке UTF-8. gRPC не используется (docs/architecture.md §4.1).
  • Единая входная точка. Внешний трафик идёт через api-gateway (Nginx); шлюз терминирует TLS, маршрутизирует запросы и добавляет X-Request-Id (docs/architecture.md §3.2). Прямых обращений к сервисам минуя шлюз нет.
  • Аутентификация. Заголовок Authorization: Bearer <JWT>. Токены подписываются RS256; каждый сервис проверяет подпись локально по кэшу JWKS (GET /.well-known/jwks.json), не обращаясь к auth-service на каждый запрос (docs/architecture.md §6.1). Роли (candidate, employer) берутся из claim-ов, совместимых с Keycloak (sub, realm_access.roles).
  • Версионирование. Текущая версия контракта — 1; она передаётся заголовком X-Api-Version (по умолчанию 1). Обратно совместимые изменения версию не меняют, несовместимые вводят новую (2). Пути версию в URL не содержат.
  • Пагинация. Списочные методы принимают page (с нуля), size и sort и возвращают объект вида { "items": [...], "page": 0, "size": 20, "total": 123 }.
  • Идемпотентность. Для небезопасных POST-операций (регистрация, формирование подборки, отправка приглашения, ответ в сессии) поддерживается заголовок Idempotency-Key: повтор с тем же ключом возвращает прежний результат без повторного эффекта. Событийные потребители идемпотентны по event_id (docs/architecture.md §4.2).
  • Идентификаторы и время. Идентификаторы — строки; временные метки — UTC в формате ISO-8601.
  • Трассировка. X-Request-Id из шлюза распространяется в события как correlation_id и дублируется в теле ошибки (§2).

2. Модель ошибок

Все сервисы возвращают единый конверт ошибки с типом содержимого application/problem+json. Корневой ключ error — единственный; тело имеет вид:

{
  "error": {
    "code": "validation_error",
    "message": "Понятное человеку описание",
    "details": [ { "field": "email", "issue": "invalid_format" } ],
    "request_id": "…",
    "timestamp": "2026-10-06T12:00:00Z"
  }
}

Поле details опционально и используется для ошибок валидации. Базовые коды:

HTTP code Когда возвращается
400 validation_error Некорректные данные или параметры запроса
401 unauthenticated JWT отсутствует, истёк или невалиден
403 forbidden Роль или право не позволяют выполнить операцию
404 not_found Ресурс не найден
409 conflict Конфликт состояния или уникальности (дубликат, повтор без Idempotency-Key)
413 payload_too_large Превышен допустимый размер тела (например, загрузка PDF-резюме)

Прочие статусы (в том числе 429 и 5xx) используют тот же конверт, чтобы клиент обрабатывал ошибки единообразно.

4. Конфигурация и секреты

Конфигурация - 12-factor, через переменные окружения. .env.example коммитится, .env в .gitignore; секреты в репозиторий не попадают, в CI встроена проверка (docs/architecture.md §7.2).

Переменная Назначение
POSTGRES_HOST, POSTGRES_PORT Адрес единого инстанса PostgreSQL
POSTGRES_DB Имя базы
AUTH_DB_ROLE, AUTH_DB_PASSWORD Роль и пароль схемы auth
CANDIDATE_DB_ROLE, CANDIDATE_DB_PASSWORD Роль и пароль схемы candidate
... (аналогично по сервисам) Отдельная роль на каждую схему
RABBITMQ_DEFAULT_USER, RABBITMQ_DEFAULT_PASS Доступ к брокеру

SMTP_HOST, SMTP_PORT Почта (dev - Mailpit)
GATEWAY_TLS_CERT, GATEWAY_TLS_KEY TLS-сертификат шлюза (демо - self-signed)

TOPOLOGY A. Один контейнер PostgreSQL, по одной схеме и роли БД на сервис (auth, candidate, fsp, assessment, selection, employer, outreach, notification), плюс брокер RabbitMQ. Кросс-схемный доступ запрещён конвенцией (docs/architecture.md §5). Миграции Flyway применяются каждой службой в своей схеме.

Миграция A → B. Переход на физический PostgreSQL на сервис - конфигурационное изменение: обновление строк подключения (POSTGRES_HOST/порт на сервис) и перенос PGDATA схемы; код и контракты не меняются (docs/architecture.md §5.4). Решение зафиксировано в docs/assumptions.md.

TLS на демо - self-signed сертификат; путь к нему задаётся переменными выше. Для локального запуска без HTTPS предусмотреть включение gateway-маршрутов через http.

5. Проверка работоспособности и типовые проблемы

Проверки каждого сервиса (docs/architecture.md §7.1):

  • /healthz - liveness: процесс жив;
  • /readyz - readiness: доступны БД и брокер;
  • /metrics - метрики в формате Prometheus (опциональный profile).

Быстрая проверка состояния:

docker compose ps          # все сервисы healthy
curl -fsS http://localhost:<port>/healthz
curl -fsS http://localhost:<port>/readyz

Smoke-тест compose. Скриптованный порядок: docker compose up → зелёные healthcheck → seed → скриптованный e2e-сценарий (docs/architecture.md §7.3). Тот же прогон закрывает требование «по запросу жюри команда демонстрирует запуск и работу кода» (docs/requirements/nonfunctional.md, «Качество кода») и выполняется одной командой на чистом окружении.

6. Демонстрационный сценарий и видео-фолбэк

Сквозной сценарий демонстрации повторяет целевой путь ТЗ (docs/requirements/user-flow.md) и детализацию шагов по ролям (docs/user_flow.md §4):

  1. Регистрация соискателя - email и подтверждение адреса; письмо перехватывается Mailpit (http://localhost:8025).
  2. Опрос и тестирование - опрос по отрасли и специализации, самостоятельный выбор предполагаемого грейда, тест на заявленный грейд (docs/testing_model.md).
  3. Присвоение категории - по итогам попытки фиксируется категория (специализация × грейд), карточка становится видимой.
  4. Поиск работодателем - работодатель открывает нужную категорию, видит ранжированную подборку (docs/selection.md).
  5. Выход на контакт - LHH-сценарий: приглашение конкретному кандидату с уровнем заработной платы, статусы приглашения, раскрытие контактов после принятия.
  6. Классический отклик [ext] - просмотр вакансий и отклик, если модуль реализован (границы - docs/mvp_scope.md).

Отдельно на демонстрации объясняются механика тестирования и механика подбора с обоснованием (docs/testing_model.md, docs/selection.md). Работа API и контракты показываются через /docs на шлюзе и через docs/api.md §3.9.

Видео-фолбэк. Если развернуть публичный прототип невозможно, по условиям ТЗ прикладывается демонстрационное видео работы прототипа и чёткая инструкция по локальному запуску, позволяющая эксперту развернуть решение самостоятельно (docs/requirements/acceptance.md, «Презентация и развёртывание»). Этой инструкцией служит настоящий документ; видео повторяет шаги §6 на локально поднятом стеке (§3).

Границы MVP

Назначение документа

Документ фиксирует границу MVP платформы PullHire: что входит в обязательную реализацию, что вынесено в опциональные срезы второй очереди и что сознательно не реализуется. Граница опирается на ТЗ (docs/requirements/overview.md, «Границы платформы»; docs/requirements/acceptance.md, «Что вне MVP» и «Что будет плюсом»), критерии оценки (docs/requirements/evaluation.md) и зафиксированные решения команды (docs/assumptions.md §9).

Связанные документы перечислены в §6.

Вне рамок: детальное описание каждой механики (оно в профильных документах), план-график работ и оценка трудоёмкости.

1. Принципы границы MVP

  • Сквозной путь важнее ширины. Обязательный сценарий соискателя (регистрация → опрос → грейд → тест → категория) и основной сценарий работодателя (потребность → подборка → приглашение) реализуются целиком; вторичные потоки — по остатку.
  • Ядро ценности — LHH-механика. Инициатива выхода на контакт принадлежит работодателю; это смысловой центр и главный критерий оценки (docs/requirements/overview.md, «Постановка задачи»).
  • Опциональные срезы проектируются полностью, реализуются во вторую очередь. Судье показывается проработанный подход; код — после ядра.
  • Граница привязана к критериям оценки. Обязательный объём максимизирует баллы ядра, опциональная часть — критерий «Дополнительный функционал» (7%).
  • Расширения помечаются [ext], а необязательные для MVP срезы — [opt]; параметры и решения фиксируются в docs/assumptions.md.

2. Входит в MVP

2.1. Роли и сценарии

  • Две роли: candidate и employer; роль фиксируется при регистрации.
  • Регистрация по электронной почте с подтверждением адреса (docs/requirements/roles.md, правило 4).
  • Разграничение доступа по ролям: кандидат видит только свои приглашения, работодатель — банк кандидатов и свои приглашения.
  • Кабинет кандидата: профиль, тестирование, категория и грейд, приглашения, настройки приватности.
  • Кабинет работодателя: профиль компании, описание потребности, подборка, поиск, выход на контакт.
  • Пошаговые пути — docs/user_flow.md §2–§3; сущности — docs/data_model.md §4, docs/data_model.md §8.

2.2. Профиль и резюме кандидата

  • Заполнение профиля вручную по форме.
  • Загрузка PDF с автораспознаванием полей (ФИО, контакты, стек, грейд, роли, стаж) — правилами; ML/NLP-разбор относится к §3.4.
  • Автогенерация стандартизированного PDF-профиля.
  • Настройки приватности и согласия на обработку и публикацию данных профиля (docs/requirements/profiles.md).
  • Владелец «что видно» — candidate-service (docs/architecture.md §3.1); данные — docs/data_model.md §4.

2.3. ФСП-интеграция

  • Связывание и отвязывание ФСП ID в настройках профиля.
  • Получение достижений через mocked-адаптер реестра (реального API в рамках хакатона нет).
  • Отображение достижений работодателю и корректная обработка случая «нет истории».
  • Схема интеграции — docs/fsp_integration.md; сущности — docs/data_model.md §5.

2.4. Грейд-тестирование

  • Обязательный конвейер при регистрации: опрос по отрасли и специализации → самостоятельный выбор заявленного грейда → тест на заявленный грейд → автоматическое присвоение категории.
  • MVP-форма грейд-теста состоит только из автопроверяемых форматов: задачи с кодом, закрытые вопросы, короткий ответ. Свободные ответы («предложить подход») в MVP-форму грейд-теста не входят (Решение D, docs/assumptions.md §9); они перенесены в регулярные задания (§3.1).
  • Грейд не понижается принудительно; повышение и понижение — по инициативе кандидата; cooldown смены грейда = 1 месяц.
  • Механика — docs/testing_model.md; сущности — docs/data_model.md §6.1.

2.5. Категории и подборка

  • Категория = специализация × грейд; присваивается по результату теста.
  • Внутрикатегорийное ранжирование по силе подтверждённого профиля и достижениям ФСП.
  • Подборка формируется на основе описания потребности работодателя; выдача сопровождается краткой объяснимостью.
  • Поиск по банку кандидатов с фильтрами: специализация, грейд, категория, стек, наличие подтверждённых достижений ФСП; уточнение запроса без потери ранее полученной подборки.
  • Механика — docs/selection.md; сущности — docs/data_model.md §7.

2.6. Приглашения и выход на контакт (LHH)

  • Инициатива у работодателя: просмотр категоризированной базы и направление приглашения конкретному кандидату.
  • Уровень заработной платы указывается обязательно; приглашение не требует привязки к опубликованной вакансии.
  • Статусы приглашений: отправлено, просмотрено, принято, отклонено.
  • Контактные данные раскрываются работодателю только после принятия приглашения (или самостоятельного отклика, если реализован срез §3.2).
  • Механика — docs/selection.md; сущности — docs/data_model.md §9.1; правила — docs/requirements/roles.md, правила 1–3.

2.7. Архитектура и инфраструктура

  • Микросервисы: auth, candidate, fsp, assessment, selection, employer, outreach, notification, плюс api-gateway и SPA.
  • Backend: Java 21 + Spring Boot, Gradle, RabbitMQ, Flyway; frontend: React/Next.js.
  • Топология A: одна PostgreSQL, схема и роль на сервис; миграция A → B документируется.
  • Контейнеризация (Dockerfile, docker-compose), OpenAPI-спецификация, CI.
  • Детали — docs/architecture.md, docs/deployment.md, docs/api.md, docs/stack.md.

  • Открытый, не скомпилированный и не обфусцированный код; лицензии MIT/Apache-2.0/BSD или реестр отечественного ПО.
  • Кроссплатформенный веб-сервис для современных десктопных браузеров.
  • Источник — docs/requirements/nonfunctional.md; развёртывание — docs/deployment.md.

3. Опциональные срезы (вторая очередь)

Каждый срез ниже проектируется полностью, но реализуется по остаточному принципу; все они дают вклад в критерий «Дополнительный функционал» (docs/requirements/evaluation.md, критерий 6, 7%). Срезы, необязательные для MVP, помечены [opt].

Маркировка. Срез целиком помечается [opt]; сущности и эндпоинты внутри среза — [ext].

3.1. Регулярные задания работодателей [opt]

  • Полная механика — optional-MVP: каденс n = 7 дней, промпты работодателя по вакансиям, добровольная подписка кандидата, случайный розыгрыш одного задания на окно, сдача, атрибут свежести профиля.
  • Свободные ответы («решить» / «предложить подход») живут именно здесь, в периодических заданиях: их оценивает работодатель вручную (статусы positive | negative | unreviewed), без нагрузки 24/7. В MVP-грейд-тест свободный ответ не входит (§2.4).
  • Результаты заданий никогда не изменяют грейд, категорию или историю грейда — обновляется только атрибут свежести профиля (display-only).
  • Спецификация — docs/periodic_tasks.md; сущности — docs/data_model.md §6.2–6.3.

3.2. Классический поток вакансий и откликов [opt]

  • Публикация вакансий работодателем (создание, редактирование), общий список вакансий, самостоятельный отклик кандидата, список своих откликов и их статусов.
  • Сценарий дополнителен к основной LHH-механике: желателен, но не обязателен для MVP.
  • Реализуется как опциональный модуль в outreach-service с документированным путём выделения (docs/architecture.md §3.4); сущности — docs/data_model.md §9.3.

3.3. Мобильная адаптивность [opt]

  • Адаптивная вёрстка для мобильных устройств и планшетов — опционально для MVP (docs/requirements/nonfunctional.md, «Платформенность»).

3.4. ML/NLP-парсинг резюме [opt]

  • Применение технологий машинного обучения и обработки естественного языка для разбора резюме, категоризации кандидатов и подбора рассматривается как преимущество при оценке (docs/requirements/acceptance.md, «Что будет плюсом»).
  • В MVP работает rule-based fallback; ML/NLP-воркер — расширение [ext] (docs/architecture.md §3.4).

4. Не входит в MVP

  • Защита от фиктивных вакансий и недобросовестных работодателей. ТЗ ожидает здесь не рабочую реализацию, а концепцию и архитектурный подход, дорабатываемый с ФСП после хакатона (docs/requirements/overview.md, «Границы платформы»). Сюда же относятся верификация компании-работодателя и модерация вакансий (docs/requirements/roles.md, правило 4).
  • Интеграция с внутренними ATS-системами работодателей. Ожидается только концепция (docs/requirements/acceptance.md, «Что будет плюсом»).
  • Свободные ответы в грейд-тесте. Исключены из MVP-формы (Решение D, docs/assumptions.md §9): обязательны только автопроверяемые форматы; свободный ответ допустим только в регулярных заданиях (§3.1) и как [ext]-расширение оценивания.
  • Реальный API реестра ФСП. Доступ и описание структуры данных не предоставляются — работа на mock/synthetic данных (docs/requirements/acceptance.md).
  • Публичная витрина чужих вакансий и парсинг сторонних площадок — вне продукта по постановке задачи (docs/requirements/overview.md).

4.1. Концепция защиты от фиктивных вакансий и недобросовестных работодателей

Post-MVP. Ниже — только концепция и архитектурный подход, дорабатываемый с ФСП после хакатона; в MVP не реализуется. Ждём от этого пункта именно концепцию, а не код (docs/requirements/overview.md, «Границы платформы»; docs/requirements/roles.md, правило 4).

  • Уровни доверия работодателя (employer trust/verification tiers). Компания проходит поэтапную верификацию (подтверждение домена и юрлица, ручная проверка реквизитов, сверка с внешними реестрами, в перспективе — сигналы ФСП); уровень доверия отображается кандидату и управляет доступом к выходу на контакт.
  • Репутация работодателя. Накапливаемые метрики поведения (доля принятых приглашений, доля «нет ответа», жалобы за период, полнота профиля компании) формируют видимый кандидату репутационный балл без раскрытия персональных данных.
  • Жалобы кандидатов (candidate reports). Кандидат может пожаловаться на вакансию или поведение работодателя; жалоба попадает в очередь модерации, влияет на уровень доверия и может инициировать карантин.
  • Сигналы фиктивной вакансии (fake-vacancy signals). Совокупность признаков: некорректные/недостижимые контакты; дублирующиеся или шаблонные объявления; несоответствие заявленной зарплаты и стека; аномально высокая доля приглашений без ответа (no-response rate); признаки массового сбора резюме без намерения найма.
  • Поток модерации и карантина (moderation/quarantine flow). Сигналы агрегируются в скоринг риска; при превышении порога объявление/аккаунт переводятся в карантин (скрытие из выдачи) до ручного разбора модератором; решения аудируются, ложноположительные сценарии предусматривают аппеляцию. Концепция дополняет, но не заменяет верификацию компании и модерацию вакансий (docs/requirements/roles.md, правило 4).

4.2. Концепция интеграции с ATS

Post-MVP. Ниже — только концепция и архитектурный подход; в MVP не реализуется. ТЗ ожидает концепцию (docs/requirements/acceptance.md, «Что будет плюсом»).

  • Изолированный модуль-адаптер. Интеграция оформляется как отдельный адаптер (по образцу шва fsp-service), а не как встроенная логика ядровых сервисов.
  • Исходящая синхронизация статусов. Адаптер выгружает в ATS работодателя статусы приглашений и откликов (отправлено/просмотрено/принято/отклонено), при необходимости — событие принятия и раскрытие контакта.
  • Целевые системы. Greenhouse/Workable/Lever-подобные ATS; различия скрыты за адаптером, ядро о них не знает.
  • Стабильная граница контракта. Обмен идёт через существующую событийную/контрактную границу (события жизненного цикла приглашения и стабильный интерфейс адаптера); ядровые сервисы не связываются с ATS напрямую — сопряжение отсутствует (no core coupling).

5. Обоснование границ

  • Отслеживаемость решений. Параметры и отклонения зафиксированы в docs/assumptions.md; состав реализованного против отложенного подводится в docs/final_summary.md.

1. Общая легенда пути

Платформа связывает напрямую только работодателя и соискателя. Путь двусторонний: кандидат проходит обязательный онбординг и становится видимым, работодатель описывает потребность и по ней получает подборку, после чего сам выходит на контакт. Ключевые инварианты пути:

  • Кандидат невидим работодателям до события assessment.category_assigned. До присвоения категории он не появляется в поиске и подборке (docs/testing_model.md §8).
  • Контактные данные закрыты до принятия приглашения. Работодатель не видит контакты, пока кандидат не принял приглашение (или не откликнулся сам, если реализован классический поток) — docs/requirements/roles.md, правило 2.
  • Инициатива выхода на контакт — у работодателя (LHH-механика) — docs/requirements/overview.md, «Постановка задачи».

Схема путей:

Кандидат:      регистрация → согласия → профиль → ФСП ID → опрос → выбор грейда → тест
               → assessment.category_assigned → карточка видна работодателю
               → приглашение → принятие → раскрытие контактов

Работодатель:  регистрация → компания → описание потребности → подборка + объяснимость
               → поиск и фильтры → приглашение → (после принятия) контакты

Каждый шаг ниже представлен таблицей «Шаг / Действие в интерфейсе / Результат».

2. Grade-change cooldown = 1 месяц

Что

ТЗ требует ограничить частоту смены грейда, но конкретный интервал оставляет команде (docs/requirements/overview.md, «Постановка задачи»).

Решение

Cooldown смены грейда = 1 месяц. Контролируется таблицей cooldowns схемы assessment; проверка права — эндпоинт /assessment/grade-eligibility.

Источник

docs/requirements/testing.md («Ограничение смены грейда»); docs/requirements/overview.md («…не чаще одного раза в три месяца — конкретный интервал команда выбирает сама»).

Обоснование

1 месяц — минимально достаточный интервал, чтобы новая попытка следовала за реальным ростом кандидата, а не за «перебором» сложности, и при этом не завышает входной барьер в демо. Отдельная таблица вместо поля истории развязывает правило и аудит.

Влияние

docs/testing_model.md §7.3; docs/data_model.md §6.1 (cooldowns); API assessment-service.

Связанные вопросы

3. Периодические задания: n = 7, синхронные окна, opt-in

Что

ТЗ задаёт идею регулярных коротких заданий, но не определяет каденс, объём, участие и вес свежести.

Решение

  • n = 7 дней — глобальная константа обоих каденсов (промпты работодателя и выдачи кандидатам); дедлайн d = n;
  • окна глобальные синхронные (не per-account rolling), идемпотентность через cycle_date;
  • участие — opt-in, по умолчанию ВЫКЛЮЧЕНО; согласие task_participation;
  • ровно одна выдача на кандидата в окно; дедупликация на уровне задания (task-level);
  • [ext] лимит повторов re-offer cap = 2;
  • пул ограничивается специализацией кандидата (обязательный фильтр); фильтр по грейду — [ext];
  • свежесть профиля ProfileFreshness — display-only, в ранжирование не входит.

Источник

docs/requirements/testing.md («Регулярные задания»); docs/requirements/roles.md («Кандидат»; «желательно, но не обязательно для MVP»).

Обоснование

Синхронные окна упрощают идемпотентность и допускают повторный запуск планировщика без дублей. Opt-in защищает кандидата и соответствует 152-ФЗ. Display-only свежести исключает «игру с механикой» и ранговый выигрыш за счёт объёма заданий: задания никогда не меняют грейд и категорию (hard rule).

Влияние

docs/periodic_tasks.md §2–§7; docs/data_model.md §6.2–6.3; docs/mvp_scope.md §3.1.

Связанные вопросы

docs/backlog/closed_questions.md — Q-2.

4. Содержимое каталога специализаций и грейдов

Что

Решение

  • специализации (MVP): backend, frontend, fullstack, mobile, devops, qa, data, ml;
  • грейды (MVP): intern, junior, middle, senior, lead.

8. Топология БД: TOPOLOGY A и путь A → B

Что

Требование удерживать память в разумных пределах и микросервисная декомпозиция конфликтуют при выборе числа экземпляров СУБД.

Решение

9. Свободные ответы вне MVP грейд-теста (Decision D)

Что

Свободные ответы («предложить подход») требуют содержательной проверки, обеспеченность которой в контуре MVP под вопросом.

Решение

Decision D. Свободные ответы исключены из MVP-формы грейд-теста; MVP-форма содержит только автопроверяемые форматы (§6). Свободный ответ остаётся в продукте только в регулярных заданиях работодателей, где оценивается работодателем (статусы positive | negative | unreviewed), без нагрузки 24/7.

Расширение [ext] — оценивание свободных ответов российским облачным LLM по фиксированной человеческой рубрике:

  • авто-вердикт допустим только при ≥ 8/10 или ≤ 3/10; всё промежуточное и любой прокторинг-флаг → очередь человеческой проверки;
  • очередь — пакетно, в рабочие часы, SLA 24–48 рабочих часов (не 24/7);
  • никогда не auto-fail; ключ оценивания и сложность b LLM не определяет;
  • пиннинг версии модели и лог хеша промпта на каждый вердикт, temperature = 0;
  • fallback при недоступности API — задание исключается из скоринга, попытка пересчитывается (безопасно за счёт якорей и эквайтинга);
  • локальный хостинг LLM исключён требованиями к железу (docs/requirements/nonfunctional.md, «Аппаратные требования»).

Источник

docs/requirements/testing.md («Формат заданий», «Регулярные задания»); docs/requirements/acceptance.md («Элементы, прорабатываемые самостоятельно»); docs/requirements/nonfunctional.md.

Обоснование

Автопроверяемые форматы снимают риск необеспеченной проверки в MVP и сохраняют сопоставимость результата. Перенос свободного ответа в периодические задания даёт ему обеспеченную оценку человека и не создаёт зависимости от 24/7-контура.

Влияние

docs/testing_model.md §3.1, §3.6, §9.2; docs/periodic_tasks.md §6.1; docs/mvp_scope.md §2.4, §3.1, §4; docs/validation.md.

10. Политика удаления аккаунта

11. Якорение периодических заданий (вакансия/потребность)

Что

Модуль публикации вакансий — [ext] (см. docs/mvp_scope.md), поэтому на MVP у работодателя может не быть опубликованной вакансии; при этом регулярные задания должны выдаваться и в этом случае. Требуется определить, к чему якорится задание и по какому признаку строится пул выдачи.

Решение

  • базовое якорение — на вакансию: Task.vacancy_id (логическая ссылка на outreach.vacancies.id, [ext]); в fallback-режиме промпт также несёт EmployerTaskPrompt.need_id;
  • если вакансия не опубликована (модуль [ext] не построен) — задание якорится на «описание потребности»/компанию работодателя через логическое поле Task.need_id (employer.needs.id);
  • оба поля якоря NULLable; заполняется ровно одно из них;
  • фильтр розыгрыша (пул выдачи) поддерживает оба якоря: задание попадает в пул, если связано с вакансией либо с потребностью;
  • обязательный фильтр по специализации кандидата и опциональный [ext] фильтр по грейду сохраняются без изменений.

Источник

docs/requirements/roles.md («Кандидат», «Регулярные задания» — желательно, но не обязательно для MVP); docs/requirements/testing.md («Регулярные задания»); docs/mvp_scope.md (модуль вакансий — [ext]).

Обоснование

Без логического якоря Task.need_id fallback-розыгрыш невозможен: работодатель без опубликованной вакансии не смог бы получить задание, и механика регулярных заданий зависела бы от [ext]-модуля. Два NULLable-якоря позволяют строить пул выдачи независимо от наличия вакансии, не нарушая HARD RULE об отсутствии cross-schema FK.

Влияние

docs/data_model.md §6.2 (Task.need_id, EmployerTaskPrompt.need_id, enum action), §2 (ERD-связь); docs/periodic_tasks.md §3–§5; docs/mvp_scope.md.

  • Мобильная адаптивность — [opt]; целевой минимум — десктопные браузеры (docs/mvp_scope.md §3.3).
  • Защита от фиктивных вакансий и ATS — только концепция и архитектурный подход, без реализации (docs/mvp_scope.md §4).
  • Реальный API реестра ФСП — mock-адаптер и синтетические данные; модель устойчива к неизвестному контракту (docs/fsp_integration.md §4, §7).
  • Калибровка тестов — IRT-lite (1PL), сложности провизорны до накопления данных; MST — fallback (docs/testing_model.md §3.5, §5.3).
  • Топология данных — одна PostgreSQL (TOPOLOGY A) со схемой и ролью на сервис; переход к физическому разделению — конфигурационный (docs/architecture.md §5.2).
  • Инфраструктурные упрощения MVP — Compose DNS вместо discovery, Nginx вместо BFF, без K8s/Consul/распределённого трейсинга; Prometheus/Grafana опциональны (docs/architecture.md §4.1, §7).
  • Оценивание LLM — только облачный LLM [ext] по фиксированной рубрике; локальный хостинг исключён требованиями к железу (docs/assumptions.md §9).

Журнал закрытых вопросов

Назначение документа

Единый журнал истории вопросов, поднимавшихся при сборке пакета PullHire, и их закрытия. Дополняет реестр ../assumptions.md (зафиксированные решения) и не дублирует его: здесь — вопрос, откуда он возник, требуемое действие и итоговый статус. Нумерация сквозная по двум пространствам: Q-N (вопросы и ответы) и TD-N (технический долг).

Связанные документы: ../assumptions.md, ../testing_model.md, ../periodic_tasks.md, ../fsp_integration.md, ../mvp_scope.md, ../worklog.md.

Источники требований: docs/requirements/acceptance.md, docs/requirements/testing.md, docs/requirements/overview.md, docs/requirements/profiles.md, docs/requirements/nonfunctional.md.

Вне рамок: сами принятые решения как таковые (они в ../assumptions.md); здесь — только динамика закрытия.

1. Формат записи

Каждая запись — подраздел ### Q-N. или ### TD-N. со полями:

  • Что — суть вопроса;
  • Откуда — документ, где вопрос возник;
  • Действие — что требовалось или было сделано;
  • Статус — один из вердиктов: решён командой, закрыт ответом из требований, осознанная граница, вне объёма;
  • Резолюция — итог со ссылкой на ../x.md или docs/requirements/x.md.

Ссылки из docs/backlog/ на authored-документы — ../x.md; на источники требований — docs/requirements/x.md.

2. Группа Q. Вопросы и ответы (Q-N)

Q-1. Совместимость с Keycloak

  • Что: обязательна ли совместимость авторизации с Keycloak (ФСП ID «в дальнейшем» будет работать на базе Keycloak).
  • Откуда: docs/requirements/nonfunctional.md («Аутентификация»); docs/requirements/profiles.md («Связь с ID участника ФСП»).
  • Действие: принять решение о способе аутентификации; при выборе Keycloak-совместимого пути обеспечить форму claim-ов и JWKS.
  • Статус: закрыт ответом из требований.
  • Резолюция: совместимость — ориентир, не требование; выбран JWT RS256 с Keycloak-совместимыми claim-ами (sub, realm_access.roles) и /.well-known/jwks.json; см. ../fsp_integration.md §2, ../architecture.md §6.1.

  • Резолюция: форматы выбирает команда — закрытые вопросы, короткий ответ, задачи с кодом; свободный ответ вне MVP-грейд-теста (Decision D). См. ../assumptions.md §6, §9; ../testing_model.md §3.1.
